# Languages

An app shows a locale: the language of the strings MyGo writes itself, and
the one an app asks about to write its own. It follows the user's preferred
language by default, and `App.SetLocale` changes it while the app runs.

An app's own strings are its own: MyGo matches locales and says what its
own menus and controls say, and `i18n.Catalog` keeps an app's texts if it
likes. Writing counts, numbers and dates the way a language does is the work
of a library of the Unicode CLDR: `golang.org/x/text` in Go, `Intl` in a
page.

## The locale an app shows

`App.Locale` returns the locale the app shows as a language tag, such as
`en-US` or `zh-Hant-HK`. `App.SetLocale` makes a tag that locale, and an
empty tag follows the user's preferred language again. `App.SystemLocale`
is the user's preferred language whatever the app shows, as Electron's
`app.getPreferredSystemLanguages()[0]`:

```go
mygo.App.Locale()          // "en-US"
mygo.App.SetLocale("zh-Hans")
mygo.App.Locale()          // "zh-Hans"
mygo.App.SystemLocale()    // "en-US"
mygo.App.SetLocale("")     // follow the system again
```

The user's preferred language is the first of the preferred languages on
macOS, the display language on Windows (not the language of the regional
formats, which may be another), the language of the environment on Linux
(`LC_ALL`, `LC_MESSAGES`, `LANG`) and `navigator.language` in a browser.

The menus, the controls of the native UI and the app follow it at once: the
calendar of a date picker says its month names in Chinese after
`SetLocale("zh-Hans")`, without restarting the app or reopening the window.
It is safe from any goroutine. Calls made before the main thread gets to
them are folded into one, so a language switched in quick steps is painted
once, in the last language, and the app hears `OnLocaleChanged` for that one
only.

`App.OnLocaleChanged` tells an app that the locale it shows changed, in time
to rebuild what it shows: `SetLocale` set another, or the user's preferred
language changed while the app follows it. A call that changes nothing the
app shows, as `SetLocale("en-US")` while the user prefers en-US, or a change
of the system's regional formats, tells nobody. The call comes on the main
thread, and it is also where an app with its own strings picks the language
it writes them in:

```go
mygo.App.OnLocaleChanged(func(locale string) {
	win.Update(func() { view.lang = locale })
})
```

A language menu is a menu of the languages the app has, each setting its
tag:

```go
ui.MenuButton(c, "Language", func(m *ui.Menu) {
	for _, l := range []struct{ tag, name string }{
		{"", "Follow the system"},
		{"en", "English"},
		{"zh-Hans", "简体中文"},
		{"zh-Hant", "繁體中文"},
	} {
		if m.Item(l.name).Chosen() {
			mygo.App.SetLocale(l.tag)
		}
	}
})
```

Pages of a web frontend hear it as well. The bridge a page runs on carries
the tag as `mygo.locale` from document start, before the page's own
scripts, and the app tells every open page when it changes, with the new
tag:

```ts
mygo.locale                      // "zh-Hans"
mygo.on("mygo:locale", (tag) => { … })
```

[`mygo-runtime`](frontend.md) wraps both: `locale()` returns the tag the app
shows now, and `onLocaleChange` subscribes to it. A page loaded later, by a
reload or a navigation, starts with the current locale, so a frontend can
pick its language once as it starts. Its listeners hear of a locale the page
did not have only: never as a page loads, unless the locale changed while it
was loading.

The texts of a frontend stay the frontend's own business: keep them in its
own i18n and pick the language with the tag it hears, as an app picks its
strings with `App.OnLocaleChanged`. macOS and Windows report a change of the
system's language while the app runs, and an app following the system follows
it; Linux does not report it, and `App.SetLocale` is how the language changes
there.

## Matching a locale

The desktop reports a locale in whatever form it likes: `en-US`,
`zh_Hant_TW.UTF-8`, `sr_RS@latin`. `i18n.Match` picks the language an app
has that best suits it:

```go
i18n.Match("zh-TW", []string{"en", "zh-Hans", "zh-Hant"}) // "zh-Hant"
i18n.Match("zh-HK", []string{"en", "zh-TW"})              // "zh-TW" (one script, two regions)
i18n.Match("pt-PT", []string{"en", "pt-BR"})              // "pt-BR"
i18n.Match("sr_RS@latin", []string{"en", "sr-Latn-RS"})   // "sr-Latn-RS"
i18n.Match("es-MX", []string{"en", "es-419", "es-ES"})   // "es-419" (Latin America holds Mexico)
i18n.Match("es-MX", []string{"en", "es-ES"})             // "es-ES"
i18n.Match("nb-NO", []string{"en", "no"})                // "no"
```

It reads the language, the script and the region of both sides, and compares
those rather than the spelling of the tags: the same language, script and
region, then the same language and script, then the same language and a
region that holds the other (`es-419`, the Spanish of Latin America, for
`es-MX`), then the language without a region, then another variant of the
language, as `pt-PT` gets `pt-BR` and `es-MX` gets `es-ES`. The old codes of
a language are the language: `iw` is `he`, `in` is `id`, and `no`,
Norwegian, is `nb`, Bokmål. It returns `""` when nothing suits, and the app falls back to
the language it writes its own strings in. A POSIX modifier names the script
a locale is written in: `sr_RS@latin` is `Latn`, `sr_RS@cyrillic` is
`Cyrl`, `az_IR@arabic` is `Arab`.

Two scripts of Chinese are not variants of each other: `zh-TW` does not
match `zh-Hans`, and Chinese with no script is Simplified, except in Taiwan,
Hong Kong and Macao. `zh` alone is read the same way: an app that has only
`zh` has Simplified, and serves no Traditional locale. The regions
of one script are variants, so `zh-HK` takes `zh-TW`.

`i18n.BaseLanguage` returns the language of a tag (`zh-Hant` is `zh`).

## The strings of the menus

The items of a menu that take their label from their role (`MenuItem.Role`,
as the Edit menu, Copy, or Quit) say it in the language of the locale the
app shows, in English, Simplified and Traditional Chinese, and say the new
language's when the locale changes. An item the app gave a label keeps it.
`mygo.UseMenuTexts` changes what a language says, or adds a language, as
`ui.UseTexts` does for the controls:

```go
mygo.UseMenuTexts(map[string]mygo.MenuTexts{
	"de": {Edit: "Bearbeiten", Undo: "Widerrufen", Redo: "Wiederholen"},
})
```

The labels that name the app, as Quit Notes, are functions of its name.
What macOS itself adds to the menus, as the items of the Services menu,
is in the languages of the app's bundle (`languages` below).

## The strings of the controls

The controls that say something of their own say it in the language of the
locale the app shows: MyGo has those strings in English, Simplified and
Traditional Chinese. A locale of another language leaves them in English.
They are the strings of the calendar and the date picker (the month and the
year it shows, the weekday initials, the buttons, the day labels assistive
technology reads, the day its week starts on), of the menu a text field
shows (Undo, Cut, Copy, Paste, Delete, Select All), of the find bar and the
search field, of the buttons that clear a search and remove a token, of the
color picker, of the split view's divider, of the inspector and of a
toolbar's More button.

The code editor (package `ui/editor`) says its own through the same texts:
the menu of a code editor (Cut, Copy, Paste, Select All, Toggle Comment, Go
to Definition, the Selection, Transform and Folding submenus), its find bar
(Find, Replace, Replace All, Match case, Match whole word, Use regular
expression, Find in selection, Previous match, Next match, Close, the count
of matches, Invalid, No results), its go to line bar and its completion
list, and its diff view, which says how many unmodified lines are hidden,
Revert and Keep, Expand up, down and all, Line 12, New text and Old text.

A package built on the controls reads the texts of the app's locale with
`Context.Texts`, and says them where it builds its own elements, as the code
editor does. The texts are the framework's own, which it keeps for its
frames until the locale or the texts change: read them, and change them
with `ui.UseTexts`.

`ui.UseTexts` changes what a language says, or adds a language the
framework has none of. A field a change leaves at its zero value keeps what
the language says, so a change says only what it changes:

```go
ui.UseTexts(map[string]ui.Texts{
	"zh-Hans": {NextMonth: "下一月"},
	"de":      {Find: "Suchen", Search: "Suchen", Clear: "Löschen"},
})
```

`ui.Texts` holds what a language needs beyond plain strings too: the
initials of its weekdays, `ui.Weekday(time.Sunday)` for a week that starts
on Sunday, and the functions that write a month and a year, a day, a count
of matches, the range of lines a go to line bar takes and the line a diff
view's gutter adds. A language added takes English for what it leaves out.
It is safe from any goroutine and makes its changes at once, and the windows
shown draw their controls again with the texts it set. One change covers the code editor too, which
reads the same texts.

## The strings of an app

The recommended shape is one Go value per language, with a field per
string, so that the compiler refuses a language that misses one:

```go
type strings struct {
	Title    string
	Deleted  func(n int) string
}

var translations = map[string]strings{
	"en": {
		Title:   "Notes",
		Deleted: func(n int) string { return fmt.Sprintf("Deleted %d notes", n) },
	},
	"zh-Hans": {
		Title:   "笔记",
		Deleted: func(n int) string { return fmt.Sprintf("已删除 %d 条笔记", n) },
	},
}
```

Pick the language from `App.Locale` with `i18n.Match`, keep a fallback for
when nothing matches, and read the strings where they are shown rather than
storing them: the locale can change at any time.

```go
func (a *app) texts() *strings {
	lang := i18n.Match(mygo.App.Locale(), slices.Collect(maps.Keys(translations)))
	if s, ok := translations[lang]; ok {
		return &s
	}
	s := translations["en"]
	return &s
}
```

The updater plugin works this way, and its `Options.Strings` shows an app
adding languages to a plugin's own window.

`i18n.Catalog` holds those values for an app that would rather not match
locales itself: `i18n.New("en", translations)` gives a catalog whose `Get`
takes a locale, whose `Languages` lists what it has, whose `Use` adds or
replaces a language while the app runs, and whose `Change` changes some
fields of a language, as `ui.UseTexts` does for the controls. It is safe
from any goroutine, and `Get` matches a locale without allocating.

A string with a count in it is often the whole of such a function. The
plural forms of a language, and the way it writes numbers and dates, are
what a library of the CLDR knows: `golang.org/x/text/message` and
`golang.org/x/text/feature/plural` in Go, `Intl.PluralRules`,
`Intl.NumberFormat` and `Intl.DateTimeFormat` in a page. MyGo leaves them
to it rather than keeping a copy of the CLDR that would fall behind.

## The languages a build declares

The strings of the controls are what the app says; what the *system* says
of the app — its name in the Finder, in a Linux launcher and in the file
properties of Windows, and the languages of its installer — comes from
[`languages`](configuration.md#languages) in the configuration, which
`mygo build` writes into the app of each platform:

```json
{
  "name": "Notes",
  "languages": [
    {"tag": "en"},
    {"tag": "zh-Hans", "name": "笔记", "comment": "随手记笔记", "keywords": ["笔记", "记事本"]}
  ]
}
```

macOS gets `CFBundleDevelopmentRegion`, the first tag, `CFBundleLocalizations`,
and a `zh-Hans.lproj/InfoPlist.strings` naming the app in each language that
names it differently: the Finder, the menu bar and the system's own dialogs
of the app say it. The folders are named as Xcode names them: a language
and its script or region (`zh-Hans`, `pt-BR`, `es-419`), Hong Kong's Chinese
`zh-HK`, and a tag of three parts its language and script (`sr-Latn-RS` is
`sr-Latn`).

Linux gets `Name[zh_CN]`, `Comment[zh_CN]` and `Keywords[zh_CN]` in its
desktop entry: the keys are the POSIX locales a launcher matches, so
`zh-Hans` is `zh_CN`, `zh-Hant` is `zh_TW`, `pt-BR` is `pt_BR` and `sr-Latn`
is `sr@latin`.

The Windows installer offers each language to a system of that language,
and the file properties of the app hold one string table per language,
which Windows shows in the language of the system. A language NSIS 3 has no
language file of fails the build of the installer, with an error that names
it; a language Windows has no ID of is skipped in the file properties, with
a warning.

A build declaring languages is separate from the app showing a locale: the
first is what the system reads of the app before it runs, the second is what
the app says while it runs.
